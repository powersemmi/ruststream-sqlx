# Базы данных SQL {#sql-databases}

`ruststream-sqlx` подключает базы данных SQL к сервису
[RustStream](https://powersemmi.github.io/ruststream/) через [`sqlx`](https://docs.rs/sqlx).
Крейт состоит из двух компонентов:

- Транзакционный outbox поверх любого брокера RustStream. При публикации сообщение
  записывается в таблицу, которой владеет сервис, а идентификатор записи передаётся вместе с
  сообщением. Подписка по этому идентификатору берёт задачу в работу и после подтверждения
  помечает её обработанной. При запуске сервис заново публикует записи, которые остались
  необработанными.
- Очереди задач в таблицах Postgres, MySQL/MariaDB и SQLite, которыми владеет сервис.

Подписка берёт строки очереди в работу в одном из трёх режимов. В режиме блокировки строк
подписка блокирует строку в транзакции, и транзакция остаётся открытой, пока обработчик не
завершит работу со строкой. В режиме аренды подписка записывает в строку срок аренды и сразу
фиксирует транзакцию: долгий обработчик не держит транзакцию открытой, а подписка продлевает
аренду, пока он работает. В режиме рекомендательных блокировок подписка блокирует ключ строки в
сеансе того соединения с базой данных, которое обслуживает доставку. Открытой транзакции при этом
нет, а строки с одинаковым ключом попадают в работу по одной. Таблицы SQLite работают в режиме
аренды или в режиме рекомендательных блокировок.

Обработчик получает сообщение из строки: кодек декодирует его из столбца полезной нагрузки.
Таблица без такого столбца работает в режиме строки. Тогда обработчик получает саму строку, то
есть структуру сервиса в том виде, в каком её прочитал sqlx, и кодек не участвует. Обработчик
пакета получает все строки, которые подписка взяла в работу за один раз, одним срезом.

Таблицу очереди может описывать отдельная структура заголовков: в ней столбцы, которые управляют
очередью, и заголовки сервиса. Тогда обработчик получает структуру сообщения. В ней лежат
структура заголовков и собственные данные сообщения, а собственный запрос сервиса может прочитать
эти данные из других таблиц через `JOIN`. Заголовки доставки строятся из полей структуры
заголовков, и только тогда, когда их кто-то читает.

Подписка, которая не нашла строк в своей очереди, ждёт интервал опроса. Публикация через брокер
сразу пробуждает подписки своей таблицы в том же процессе. В Postgres вызов `listen_notify()`
пробуждает их ещё и по уведомлениям из других процессов. Для этого брокер держит одно соединение
из пула, а каждая публикация выполняет ещё один запрос. При фиксации транзакции с уведомлением
Postgres берёт одну блокировку, общую для всего сервера, поэтому такие транзакции фиксируются по
одной. Это ограничивает нагрузку, когда в базу данных одновременно пишет много клиентов.

Если при регистрации обработчика указать `.transactional()`, он записывает данные через
транзакцию своей доставки, в любом из трёх режимов. Подтверждение фиксирует изменения обработчика
и завершает строку в одной транзакции. При любом другом результате изменения откатываются. Пока
доставка в работе, её транзакция занимает соединение из пула.

Подписка ограничивает число доставок сообщения через `max_attempts(n)`, а через `dead_letter(..)`
называет группу или таблицу, куда переходит строка, когда её попытки исчерпаны. Оба параметра
объявляются вместе. С `max_attempts(1)` строка переходит туда после первой же неудачи.

Столбцы, которые управляют очередью, играют роли, и каждая роль включает одно поведение: группу,
которую читает подписка, порядок, в котором строки берутся в работу, ключ, который сохраняет
порядок связанных строк, задержку перед переобработкой, счётчик попыток и отметку, при которой
обработанная строка остаётся в таблице, а не удаляется. По умолчанию таблица берёт текущее время с
часов хоста. Вместо них она может читать часы базы данных, и тогда все хосты получают одно и то же
время.

Таблицу очереди сервис описывает через `#[derive]` на своей структуре или вручную. При ручном
описании структура реализует трейт, а все настройки таблицы задаёт типизированный строитель.
Компилятор проверяет такое описание так же строго, как описание через `#[derive]`. Оба способа
дают одни и те же запросы и одинаковые затраты на каждое сообщение.

Для Postgres, MySQL/MariaDB и SQLite в крейте есть встроенные диалекты. Запрос, который сервис
пишет по-своему, задаётся как событие: таблица называет его в `custom(..)` у `#[derive]` или в
строителе при ручном описании, а структура реализует его трейт. Для базы данных без встроенного диалекта сервис пишет собственный диалект. Такой диалект
реализует трейт каждого режима, в котором работают его таблицы, и трейт подписок по имени. Таблица
в режиме, которого у диалекта нет, не компилируется.

Таблицы очередей принадлежат сервису. При запуске подписка проверяет, что в её таблице есть
столбцы, которые называет структура. За типы столбцов отвечает сервис. Если строка не
декодируется в структуру, подписка завершает обработку этой строки по своей политике для ошибок
декодирования.

## Где всё остальное {#where-the-rest-is}

Справочник по крейту находится на docs.rs: [`ruststream-sqlx`](https://docs.rs/ruststream-sqlx).

Обработчики, роутеры, кодеки и middleware даёт сам фреймворк, а его входные страницы начинаются
с [сайта RustStream](https://powersemmi.github.io/ruststream/).
