# Порядок: группы FIFO и ключи партиционирования

Это руководство сохраняет порядок задач: всех задач группы или задач каждого ключа, пока задачи других ключей выполняются параллельно.

`SKIP LOCKED` ускоряет захваты, потому что они пропускают строки в работе.
Из-за этого же следующая строка может уйти в работу, пока более ранняя ещё в работе или ждёт переобработки.
Очередь, задачи которой должны применяться по порядку, объявляет это в своей таблице.

Пример - сервис счетов.
Он отправляет изменения контактов в CRM, которая должна получать их в том порядке, в каком они произошли, и применяет проводки по счетам, которые должны сохранять порядок в пределах одного счёта.

`#[field(group, fifo = true)]` делает каждую группу `target` [группой FIFO](../components/subscriptions/fifo.md).
В группе FIFO в работе не больше одной строки, сколько бы воркеров, подписок и процессов её ни читали.
Первая незавершённая строка группы в порядке захвата - её голова, и захват берёт только голову.
Строки за ней ждут, пока голова в работе, в том числе под арендой другого экземпляра.
`retry()` оставляет изменение в голове, поэтому оно снова уходит раньше тех, что за ним.
`retry_after(d)` переместил бы его за строки, готовые раньше него.

Голова, которая раз за разом возвращает ошибку, держит всю свою группу.

После трёх отказов изменение перемещается в группу `crm.parked`, и головой становится следующее изменение `crm`.
Отложенное изменение ждёт там человека. Изменения за ним уже ушли без него, и это цена освобождения группы.

Группы работают бок о бок, каждая через собственную подписку, поэтому группа подходит для нескольких заранее известных потоков: по одной на внешнюю систему, по одной на клиента.
`workers(n)` не даёт подписке FIFO параллелизма: её обслуживает один воркер.

## Ключ на счёт {/* #a-key-per-account */}

Счетов в учёте много, слишком много, чтобы заводить подписку на каждый.
Важен порядок внутри одного счёта, а разные счета могут обрабатываться параллельно.

`#[field(partition_key)]` делает счёт ключом каждой строки.
Приложение монтирует `post` с [`workers_by_key(4)`](../components/subscriptions/workers.md): четыре воркера, а проводки одного счёта идут на одном из них в порядке захвата.
На такой таблице подписка держит не больше одного захвата одновременно, поэтому захваты не обгоняют друг друга.
Этот порядок действует внутри одной подписки.
Проводки одного счёта, которые должны сохранять порядок на нескольких экземплярах, помещаются в группу FIFO или в [форму рекомендательной блокировки](../components/forms/advisory.md) с ключом по счёту: она пускает строки одного ключа в работу по одной во всех процессах на сервере.

## Тестирование {/* #testing */}

Тесты в файле примера запускают сервис на SQLite в памяти.
Первый публикует изменение, которое CRM отклоняет, и изменение, которое она принимает: первое уходит три раза и откладывается, затем уходит второе.
Второй записывает голову `crm` как арендованную другим экземпляром и находит, что изменение за ней ждёт.
Третий записывает вперемешку проводки двух счетов и находит, что проводки каждого счёта применены по порядку.
Строки последних двух тестов не будят ни одну подписку, поэтому эти тесты работают на реальных часах через [`TestApp::start_live`](../components/testing/live.md) и ждут дольше интервала опроса.
