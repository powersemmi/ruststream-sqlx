    Claims

    Three ways to claim a row: a row lock held by an open transaction, a lease written into the row, and an advisory lock on a key, each priced in connections.

    The table's description picks the form. A table with no form set takes the row lock form; a locked_until column selects the lease form; advisory_lock = ".." selects the advisory lock form. The forms differ in what holds a row while its handler runs, and so in what brings the row back when the process dies.

    Row lock​

    The claim opens a transaction and selects its rows with FOR UPDATE SKIP LOCKED. A concurrent claim skips the locked rows instead of waiting for them. The transaction stays open while the handler runs, and the settlement's statement commits it, so the row and its outcome change in one commit. When the process dies, the database rolls its transactions back and the rows are due at once. The price is one connection per delivery in work, held for the whole handler. On MySQL and MariaDB the transaction opens at READ COMMITTED unless the table names a level, so the claim locks the rows it takes and not the gaps between them.

    Lease​

    The claim writes an expiry into locked_until, counts the attempt and commits at once, so the handler runs with no transaction open and no connection held. The subscription extends every lease in work each half lease, so a handler may run longer than its lease. The expiry is the delivery's token: a settlement names the expiry it holds, and it takes effect only while the row still holds it. A handler whose lease ran out while it ran, because its extensions failed or stopped, finds another claim's token in the row, and its settlement fails with SqlxBrokerError::LeaseLost. When the process dies, its rows return when their leases run out: thirty seconds unless set, in whole seconds. The host computes the expiry, because every settlement compares it, so a lease table reads the host's clock.

    Advisory lock​

    A claim selects due rows with their keys, tries each key's lock on a connection of its own without waiting, passes over a key another session holds, then takes the row while it is still claimable. Rows whose keys match go into work one at a time, so advisory_lock = "accounts-{account}" keeps each account's rows apart while other accounts run. No transaction stays open, but the connection that holds the lock stays with the delivery until it settles. When the process dies, its sessions end and the database drops their locks. A key belongs to the database, not to a table: two tables whose keys match wait for each other.

    A server older than the floor stops a subscription at startup with SqlxBrokerError::ServerTooOld: MySQL 8.0.1 and MariaDB 10.6 are the first releases that skip locked rows. A PostgreSQL advisory lock lives in the session that took it, so the form needs a direct connection or a pooler in session mode. Two processes on one SQLite file do not see each other's keys, and a row may then be delivered twice.

    In a FIFO table a claim takes only the head of its group, and nothing while another row of the group is in work. The guard in the table above takes the group in the claim's transaction, so subscriptions to one group on separate brokers keep its order too.

    The attempt is counted where the form holds the row: the row lock form counts it at settlement, in the statement that returns the row; the lease form at the claim; the advisory lock form at the take. So a crash spends an attempt in the lease and advisory lock forms, and not in the row lock form, whose rollback undoes the count with everything else. A delivery reports the attempt as it stood before its claim, so the first delivery reads 1 in every form.

    The databases document the primitives: PostgreSQL SELECT .. FOR UPDATE and advisory locks, MySQL locking reads and locking functions, MariaDB SKIP LOCKED.
