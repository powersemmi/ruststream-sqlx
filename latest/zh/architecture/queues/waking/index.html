    唤醒

    订阅在领取总是取满时持续领取，否则等待它的轮询间隔，同一 Broker 的发布或一条通知会提前结束这次等待。

    运行时轮询订阅的流时，订阅进行领取。取满上限的领取之后立即进行下一次领取，因此积压的消息无需等待即可排空。取到的行少于请求数的领取，说明队列暂时是空的，订阅进入等待。失败的领取以一个错误项到达流中，下一次领取等待一秒，因此数据库不可达时，循环不会空转。

    经 Broker 的发布会唤醒同一 Broker 上订阅了该表的订阅：Repository、路由、应答，以及测试通过测试框架发布的消息都是如此。在有组的表中，它只唤醒自己那个组的订阅。正在领取的订阅会把唤醒留给下一次等待，那次等待随即立即返回。唤醒让发布为它唤醒的每个订阅付出一次原子操作，订阅本身在每条消息上不付出任何开销。服务自己写入的行，无论用自己的 SQL 还是通过处理器的 Tx，都不唤醒任何订阅：它等待轮询间隔，或者等待一条通知。

    LISTEN/NOTIFY​

    在 PostgreSQL 上，listen_notify 让其他进程中的订阅也被唤醒。Broker 在 connect 时从连接池取一个连接，在上面监听，一直保留到 shutdown。每个订阅在第一次领取之前监听它的表的通道：通道名就是表名，表有模式时带上模式限定，如 app.jobs。Broker 的每次发布在写入之后，立即在写入该行的连接上执行 SELECT pg_notify(channel, group)；载荷为空的通知唤醒该表的每个订阅。通知失败时会记录日志，发布仍然成功：轮询间隔会让订阅取到这一行。

    PostgreSQL 在事务提交时投递通知，因此被唤醒的订阅能看到这一行。监听连接断开期间发出的通知会丢失：Broker 重新连接，并把每个订阅唤醒一次。通道名最多 63 字节，因此对限定名更长的表的订阅会在启动时停止。这个开关在 Broker 的整个生命周期内占用一个连接，并让每次发布多执行一条语句。发出通知的事务在提交时还会获取一个服务器全局的锁，因此发出通知的提交依次执行，这会限制大量并发的写入者。在其他数据库上，listen_notify 无法编译。

    服务器在 NOTIFY 一页说明了这个机制：在提交时投递，载荷小于 8000 字节，以及标识符的 63 字节限制。提交时的锁由 PostgreSQL 开发者在邮件列表中说明。
